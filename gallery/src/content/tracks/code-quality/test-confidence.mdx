## Find a missing test

**What behaviour matters, and what evidence do our tests actually provide?** Start with one question about code people use. Finish with a test you can explain, not a coverage target.

Use the Lab exercise below after [local setup](#/guide/setup), or follow the same steps in your own repository with its existing test runner.

### 1. Trace the behaviour

Open <DemoLink id="web-worker-comparison">Room to think</DemoLink>. Both calculation buttons ultimately use `countPrimes` in `demos/web-worker-comparison/compute.ts`. The function counts primes up to and including a limit; the largest allowed limit is `MAX_LIMIT`.

Read the callers and `compute.test.ts`. Separate three questions:

- Does the calculation return the right result?
- Does it reject invalid inputs?
- Does moving work to a Worker keep the interface responsive?

A unit test of the function answers the first two. It cannot establish the third. Trace imports before proposing a refactor: both buttons already share the same calculation.

### 2. Read the existing evidence

From the repository root:

```sh
npm test --workspace @lab/demo-web-worker-comparison
```

The tests cover small limits, invalid inputs and the maximum workload. The maximum case was added after an investigation found that only smaller workloads were covered: `countPrimes(2_000_000)` should return `148933`, independently checked using a sieve. No algorithm bug was found; the improvement was stronger evidence for an allowed input.

That case is already in the suite. Keep it. A completed investigation is a useful example, not a reason to add the same test twice.

### 3. Catch a regression the suite misses

The calculation also receives values through a Worker message. TypeScript types do not validate messages at runtime. Should the string `"10"` be accepted as a number? The current function rejects it.

On an experiment branch, temporarily change just this expression in `compute.ts`:

```ts
Number.isInteger(limit)
```

to:

```ts
Number.isInteger(Number(limit))
```

This resembles a convenient coercion, but weakens validation: the function now accepts numeric strings. Run the existing tests. They still pass because their invalid-input cases contain numbers, not strings.

Add this to `compute.test.ts`:

```ts
test('rejects numeric strings received at runtime', () => {
  assert.throws(() => countPrimes('10' as unknown as number), RangeError);
});
```

The cast deliberately models untrusted runtime input; it is not an example of normal typed calling code. Run the tests again. The new test should fail because the modified implementation does not throw.

Restore `Number.isInteger(limit)` and rerun with the new test present. All tests should pass. Restore only your deliberate implementation edit; keep any unrelated work. Do not commit the regression.

You have now observed three distinct results: the old suite passed a defect, the added test detected it, and the restored implementation satisfied it. The expected error comes from the function's input contract, not a copy of its algorithm.

### 4. Apply it in your own repository

Choose one real input boundary, state transition or failure path. Trace it from a caller to the logic and then to its tests. Write down what is already checked before adding anything.

Derive the expected result from the requirement, a small hand-worked example or an independent method. Copying the implementation into the test can reproduce the same mistake twice. Use your project's existing runner; adopting Node's test runner is not part of this exercise.

Verify that a small, plausible implementation regression fails the new test. Restore the correct implementation, then run the relevant surrounding tests. Keep any wider checks needed by the change. Never leave a deliberate failure in the committed code.

Finish with: **“This test establishes …; it does not establish ….”** If the existing tests already answer the question, explain that and leave them alone.

Read: [Node test runner](https://nodejs.org/docs/latest-v24.x/api/test.html) and [strict assertions](https://nodejs.org/docs/latest-v24.x/api/assert.html).
