## Find a missing test

What behaviour matters, and what evidence do your tests provide? Choose an input boundary, state transition or failure path. Follow a caller into the implementation and tests.

### Establish the contract

Derive an expected outcome from a requirement or hand-worked example before writing an assertion. Don't copy the implementation's calculation into the test.

For a Lab example, investigate `countPrimes` in `demos/web-worker-comparison/compute.ts` and its adjacent tests:

```sh
npm test --workspace @lab/demo-web-worker-comparison
```

Correct arithmetic and input validation are separate claims. Neither proves interface responsiveness. Check whether the current suite already protects your chosen behaviour.

### Check whether the test catches a mistake

Add a case if needed, then temporarily introduce a plausible regression. The test should fail for the expected reason. Restore only that deliberate edit and confirm it passes; don't commit the defect.

<details>
<summary>Example: a numeric string at a runtime boundary</summary>

`countPrimes` rejects `"10"`: TypeScript doesn't validate incoming Worker messages. Investigate whether the tests protect that contract.

Temporarily replacing `Number.isInteger(limit)` with `Number.isInteger(Number(limit))` introduces coercion. Would the existing tests detect it? Choose an assertion from the rejection contract, then verify it catches this change. Restore the original validation afterwards.

</details>

If a test stays green, investigate its inputs and assertions rather than assuming the code is safe. If it already catches the mistake, another test may add no value.

For your next case, consider whether a unit test is enough: testing a function alone doesn't prove its caller supplies the right data. Rerun surrounding checks after restoring deliberate changes.

Read [Node's test runner](https://nodejs.org/docs/latest-v24.x/api/test.html) and [strict assertions](https://nodejs.org/docs/latest-v24.x/api/assert.html).
