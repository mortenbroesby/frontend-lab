## Find a missing test

**The tests pass. Would they catch this bug?** [TDD](#/track/code-quality/tdd) starts with a failing example. Here, start with existing green tests and see what they actually protect.

### Try it: a number that isn't a number

`countPrimes` accepts numbers and rejects invalid input. But a Worker message arrives at runtime; TypeScript can't guarantee its contents.

| Input | Intended result |
| --- | --- |
| `10` | Four primes: 2, 3, 5, 7 |
| `"10"` | Reject a string instead of silently converting it |

Read `demos/web-worker-comparison/compute.ts` and `compute.test.ts`. Does the suite protect both claims?

```sh
npm test --workspace @lab/demo-web-worker-comparison
```

### Challenge the green result

Temporarily change `Number.isInteger(limit)` to `Number.isInteger(Number(limit))`. This allows coercion at the validation boundary. Predict the test outcome before rerunning.

<div className="guide-flow" role="group" aria-label="Check whether a test detects a regression">
  <div><strong>Introduce one plausible mistake</strong><span>Keep the edit small and temporary</span></div>
  <span aria-hidden="true">↓</span>
  <div><strong>Run the relevant test</strong><span>Did it fail for the intended reason?</span></div>
  <span aria-hidden="true">↓</span>
  <div><strong>Restore the implementation</strong><span>Confirm the test passes again</span></div>
</div>

If the suite stays green, add an assertion derived from the rejection contract. Check that it fails against the coercing implementation, then restore the original validation and rerun. Don't commit the deliberate defect.

<details>
<summary>What should the assertion establish?</summary>

It should establish that a numeric string is rejected—not reproduce the prime-counting algorithm. In a TypeScript test, deliberately invalid input may need an explicit type escape or expected type-error annotation. Keep that exception at the test boundary; don't weaken the production signature.

A failure for a syntax error or missing import doesn't demonstrate that the test detects coercion.

</details>

If an existing test already catches the mistake, another equivalent test may add no value.

### Pick your next blind spot

Try an input boundary, state transition or failure path in your own code. Derive the expectation from a requirement or hand-worked example before reading the implementation's answer.

**Done:** a plausible regression fails for the right reason, and restoring the behaviour makes it pass. Function tests still don't prove the caller sends the right data or the UI stays responsive; choose a broader check when that's the claim you need.

Read [Node's test runner](https://nodejs.org/docs/latest-v24.x/api/test.html) and [strict assertions](https://nodejs.org/docs/latest-v24.x/api/assert.html).
