## Investigate with Fallow

Use static analysis to make one justified improvement to a JavaScript or TypeScript project. You'll learn to interpret a finding, verify its assumptions and decide whether changing the code would actually help.

### 1. Choose a question and run a scan

Use your own repository, or follow [local setup](#/guide/setup) to use the Lab, where Fallow is already installed. In another npm project, install it locally first:

```sh
npm install --save-dev --save-exact fallow
```

Use your existing package manager and keep its manifest and lockfile together. Start with automatic discovery; don't copy this repository's configuration into another project.

From your project root, choose one question:

| Question | Command |
| --- | --- |
| Can we remove something unused? | `npx fallow dead-code` |
| Are we maintaining the same logic twice? | `npx fallow dupes` |
| Which function is hard to reason about? | `npx fallow health` |
| Where do imports form a cycle? | `npx fallow architecture` |

These commands analyse code without changing it. A scan can exit 1 because findings exceed a threshold; read the result before treating that as a tool failure. Check your installed command's `--help` when using documentation for a different version.

### 2. Follow one piece of evidence

Pick a finding near code you understand. Follow its callers before editing anything.

- **Unused code:** check whether a route, generated consumer or dynamic import loads it. Published exports may have consumers outside the repository.
- **Duplication:** determine whether the copies should change together. Independent experiments don't always need a shared abstraction.
- **Complexity:** identify the decisions that make the function difficult to follow. A named step should clarify the code, not just move the score elsewhere.
- **A cycle:** trace every import in it and decide which module should own the shared responsibility.

If there are no findings, investigate a dependency instead. In the Lab:

```sh
npx fallow dead-code --trace-dependency d3-force
```

Follow the reported import into `demos/dependency-map/index.tsx`. Find the force simulation and compare what it does with the dependency traversal in `graph.ts`: layout and impact analysis are separate responsibilities. This explains why the dependency exists without inventing unused code to remove.

In your project, replace `d3-force` with a package from its manifest. An empty trace alone isn't proof that a package can be uninstalled.

### 3. Make a decision you can verify

Remove a genuinely unused export, simplify a confusing function, correct discovery—or keep the code when it serves a useful purpose. Keeping a dependency after understanding it is a valid outcome.

For a surprising unused-code result, inspect the project model first:

```sh
npx fallow list --entry-points --plugins --workspaces
```

Check that real application entries and dynamic consumers are represented. Correct a missing entry narrowly rather than ignoring the finding wholesale. If configuration is needed, `npx fallow init` can generate it; inspect its changes before keeping them.

Rerun the original scan after your edit, then the relevant test, type check or build. Check both the intended behaviour and the finding. A smaller score doesn't establish correctness, and Fallow's coverage-related risk estimates aren't measured coverage without a supplied coverage file.

### Take it further

Try the same investigation with your existing linter or another analysis tool. Compare which evidence each provides. For team adoption, review discovery and findings before introducing a blocking CI policy or baseline; use the [official adoption guide](https://fallow.tools/docs/adoption/).
