## Protect an architecture boundary

Which dependency would make your code harder to change independently? Choose an ownership rule before choosing enforcement. A tool can't decide whether the boundary makes sense.

### Express one decision

For example: “Shared utilities must not import feature implementations.” Use directories that represent real responsibilities; don't reorganise a project to fit a tool.

In your own npm project, install dependency-cruiser and inspect its initializer:

```sh
npm install --save-dev --save-exact dependency-cruiser
npx depcruise --init
```

Use your existing package manager. Edit existing configuration rather than replacing it, and check resolver settings against your framework and aliases.

The [rules tutorial](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-tutorial.md) explains `from`, `to` and path expressions. Translate your decision into a rule using your project's paths.

In the Lab, setup already exists. Inspect `demos-stay-independent` in `.dependency-cruiser.cjs`: demos may use shared packages, but not each other's implementations. Run:

```sh
npm run check:architecture
```

### Prove the rule works

Temporarily introduce an import across your chosen boundary. Does the named rule catch it? Remove only that probe and confirm the clean result. Also check an allowed import—a rule that rejects everything isn't useful. Don't commit the probe.

For a real violation, consider moving responsibility, passing a value or revising an unsuitable boundary. Don't weaken rules merely to get a green result.

Once trusted, add the check to your existing workflow. Keep exceptions narrow. The Lab checks static source imports with SWC; MDX, Vite globs and computed imports still need review.

Read the [rule reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md) and [CLI reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md).
