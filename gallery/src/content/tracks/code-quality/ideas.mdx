# Ideas to explore

Use this repository or your own. Investigate a health question, not a target score. Keeping code unchanged can be a useful outcome.

## Dependency health

Ask why a dependency exists, where it is used and what maintenance costs. Look for unused packages, version drift or overlapping libraries.

Trace callers before changing a package. Compare package-manager data with static analysis; dynamic loading or configuration may explain apparent non-use. Outdated does not mean harmful.

Read: [npm explain](https://docs.npmjs.com/cli/v11/commands/npm-explain) and [Knip’s unused-code and dependency analysis](https://knip.dev/).

## Complexity and duplication

Pick a hard-to-explain function. Identify decisions, responsibilities and repetition. Compare simplifications with leaving it alone.

Try a small refactor with existing tests. Does extraction clarify intent or just move complexity?

Read: [ESLint’s complexity rule](https://eslint.org/docs/latest/rules/complexity) for what the metric measures, and [Fallow](https://fallow.tools/) for broader codebase analysis.

## Architecture and boundaries

Trace relationships between features, packages and utilities. Which dependency boundaries are explicit, and which rely on convention?

Trace one behaviour through imports. Visualise dependencies, investigate a surprising edge or enforce an agreed boundary. Decide what a rule protects before adding it.

Read: [dependency-cruiser’s documentation and examples](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md).

## Confidence in change

Find the test that would catch a behaviour breaking. Does a pass prove what you assumed?

Test that assumption with a reversible change on your branch. Explore a boundary case or stronger assertion. Investigate automated findings before deleting code.

Read: [Node’s test runner](https://nodejs.org/docs/latest-v24.x/api/test.html) and [Fallow’s analysis documentation](https://fallow.tools/).
