# Make code easier to change

Explore dependencies, simplify confusing code or improve a test. Use this repository or a project you know. Choose one question below and investigate it with the tools you already have.

## See what is possible

Choose a question you would like to answer:

- **Why is this package here?** [npm explain](https://docs.npmjs.com/cli/v11/commands/npm-explain/) traces why a dependency is installed. Pick a package you do not recognise and follow the chain back to something you do.
- **What could we stop maintaining?** [Knip’s getting-started guide](https://knip.dev/overview/getting-started) introduces finding unused files, exports and dependencies. Compare its approach with Fallow, which is already available in this repository.
- **What is connected to what?** [dependency-cruiser’s examples](https://github.com/sverweij/dependency-cruiser) show how imports can become diagrams and enforceable rules. Look for a surprising connection, then ask whether it makes changes harder.
- **Why is this function difficult to follow?** [ESLint’s complexity examples](https://eslint.org/docs/latest/rules/complexity) illustrate how branches contribute to a metric. Compare the number with how easy the code is to explain.

You do not need to install every tool or produce a cleanup commit. Pick one question, gather evidence and try one small improvement. Discovering that the code should stay as it is can be just as useful.

## A dependency you can explain

**“I would like to remove or update this package, but I do not know what depends on it.”** Explore unused dependencies, duplicate versions and libraries that solve overlapping problems. The interesting result is understanding the cost of keeping or changing something.

Start with one dependency from a real `package.json`. In this repository, try `npm explain react` from the root and follow one dependency chain. Find the imports and configuration that use the package. For a removal candidate, compare that evidence with static analysis: dynamic loading, scripts or build configuration can explain apparent non-use.

Stretch by comparing two libraries with overlapping responsibilities, or trying one warranted removal on your branch and running the affected checks. An outdated version is a reason to investigate, not proof that the package needs replacing.

Read: [npm explain](https://docs.npmjs.com/cli/v11/commands/npm-explain/) and [Knip’s getting-started guide](https://knip.dev/overview/getting-started). Knip is an optional tool to explore, not a required part of the Lab setup.

## Code a colleague can follow

**“This works, but I have to hold too much in my head to change it.”** Pick a function or component with several decisions, responsibilities or repeated pieces. Try explaining what it does without narrating every line.

Start by identifying its inputs, outcomes and one confusing branch. Compare the original with a small change: a better name, an early return or separating a calculation from an effect. Run the relevant tests and ask someone to read both versions. Did the change make the behaviour clearer, or merely move it into another file?

Stretch by investigating repeated code. Do the copies represent the same rule, or could they reasonably change independently? Keeping two small pieces separate may be clearer than creating a shared abstraction. A lower complexity score is supporting evidence, not the goal.

Read: [ESLint’s complexity rule and examples](https://eslint.org/docs/latest/rules/complexity) and [Fallow](https://fallow.tools/) for broader codebase analysis.

## Boundaries that make changes smaller

**“Why does changing this feature affect that one?”** Follow the connections between a screen, its data and shared utilities. Explore whether the code’s dependencies match the boundaries people think they have.

Start by tracing one behaviour through its imports. Sketch the few modules involved and mark any dependency you did not expect. In this repository, run `npm run check:architecture` and inspect one rule in `.dependency-cruiser.cjs`. The check uses dependency-cruiser, which is already installed; explain what the rule protects before changing it.

Stretch by comparing two ways to remove an unwanted connection, or expressing an agreed boundary as a rule. Check that the rule catches the intended import without blocking legitimate use. A passing check only tells you that the inspected graph satisfies the configured rules.

Read: [dependency-cruiser’s diagrams and examples](https://github.com/sverweij/dependency-cruiser) and [its rule reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md).

## Tests that answer your actual question

**“The tests are green. Would they notice this behaviour breaking?”** Choose one observable behaviour and find the assertion that protects it. Explore missing boundaries, weak assertions or tests that repeat the implementation’s assumptions.

Start with a real test in this repository or your own project. Predict a small mistake it should catch, make that reversible change on your branch and run the test. If it still passes, investigate why. Restore the implementation before strengthening the test, then verify that your assertion distinguishes the intended behaviour from the mistake.

Stretch with an edge case whose expected result you can establish independently, or compare what a unit test and an interaction test would tell you. You do not need a coverage target or a new test framework to learn something useful.

Read: [Node’s test runner](https://nodejs.org/docs/latest-v24.x/api/test.html). Use the test runner already present in your chosen project.
