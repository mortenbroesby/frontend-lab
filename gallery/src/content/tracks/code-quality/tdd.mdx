## Try test-driven development

TDD is a way to build a feature in small steps: **describe one behaviour with a test, make it work, then tidy the code.** The test helps you decide what the code should do before deciding how to implement it.

| Step | What you do | What you should see |
| --- | --- | --- |
| **Red** | Write one test for the next behaviour. | It fails because that behaviour is missing. |
| **Green** | Add just enough code to support it. | All your tests pass. |
| **Refactor** | Improve names or structure without changing behaviour. | The same tests still pass. |

### Your first experiment: a carousel's Next button

Build the rule for choosing the next item. With three items numbered **0, 1, 2**, Next should move **0 → 1 → 2 → 0**. We'll test the rule first; connecting it to a React button comes later.

**You need:** the Lab's Node 24 setup and a demo folder you can edit. No extra testing library or browser is needed. Follow [local setup](#/guide/setup) and [create a demo](#/create) if you don't have one. In the commands below, replace `your-id` with its generated folder ID.

### 1. Red: describe one step forward

Add these two files beside your demo's `index.tsx`. Write the test first.

In `selection.test.ts`:

```ts
import assert from 'node:assert/strict';
import test from 'node:test';
import { nextIndex } from './selection.ts';

test('next moves to the following item', () => {
  assert.equal(nextIndex(0, 3), 1);
});
```

In `selection.ts`, give the function a deliberately unfinished body:

```ts
export function nextIndex(current: number, count: number): number {
  return current;
}
```

For this first version, assume a non-empty list and a valid current index. Run from the repository root, replacing `your-id` with your demo's folder ID:

```sh
node --test demos/your-id/selection.test.ts
```

**Red:** the assertion should report `0` instead of `1`. A missing module or syntax error doesn't establish the behaviour yet; fix that setup problem first.

### 2. Green: make the first test pass

Change the return value to `current + 1`. Run the same test again.

**Green:** the first example now passes. Don't add wrapping, empty-list handling or a selection controller yet. Choose the next behaviour that matters.

### 3. Repeat: what happens at the end?

Append this test to `selection.test.ts`, leaving the first test in place. Don’t change `selection.ts` yet:

```ts
test('next wraps from the last item to the first', () => {
  assert.equal(nextIndex(2, 3), 0);
});
```

Run again. It should fail with `3` instead of `0`. Now implement wrapping and rerun **both** tests.

<details>
<summary>One possible next implementation</summary>

```ts
export function nextIndex(current: number, count: number): number {
  if (current === count - 1) return 0;
  return current + 1;
}
```

</details>

### 4. Refactor: improve the code, keep the behaviour

**Refactor:** improve clarity without adding behaviour. For example, compare the explicit branch with `(current + 1) % count`. Which is easier to understand here? Keep the branch if it communicates the rule better; refactoring doesn't require changing something.

Run the tests after each edit. A refactor should preserve their expectations, not rewrite them to match the implementation.

**First experiment complete:** both tests pass, and changing the wrapping rule breaks the second test. You now have examples that protect the behaviour while you change its implementation.

To rerun automatically when you save:

```sh
node --test --watch demos/your-id/selection.test.ts
```

### 5. Take it into your own feature

- **One item:** should Next keep it selected? Write the example. If it already passes, don't change the implementation unnecessarily.
- **No items:** should there be no selection, a disabled Next button or an error? Decide the contract before adding a test. The current assumption deliberately excludes this case.
- **A real interface:** connect the rule to a carousel or menu. The function tests don't prove that a button calls it or that focus moves correctly.

For UI behaviour, use your project's existing component test setup. A useful test clicks Next and checks the selected item or accessible state. Avoid asserting internal hook values or component structure. [Testing Library's principles](https://testing-library.com/docs/guiding-principles/) explain this user-facing approach; it isn't required for the Node exercise above.

### Keep the cycle useful

Start with one observable outcome. Derive the expected result from the requirement, not by repeating the implementation in the assertion. Mock an external boundary when needed, not the logic you're trying to test.

TDD is useful when the expected behaviour is clear enough to express. For exploratory visuals, try a sketch first and test stable rules as they emerge. For existing code with unclear behaviour, [find a missing test](#/track/code-quality/test-confidence) before changing it.

### Where to go next

- **Understand the approach:** [Martin Fowler: Test Driven Development](https://martinfowler.com/bliki/TestDrivenDevelopment.html) explains the cycle and the role of a list of behaviours to implement. Read this if TDD still feels like “write tests first” without a reason.
- **Test a React interaction:** [React Testing Library's annotated example](https://testing-library.com/docs/react-testing-library/example-intro/) walks through rendering, acting and checking visible results. Use it to turn “Next selects the following item” into a component test; it needs a component test environment beyond this Node-only exercise.
- **Choose better assertions:** [Testing Library's guiding principles](https://testing-library.com/docs/guiding-principles/) explain why tests should resemble how people use the interface.
- **Use the tools in this exercise:** [Node's test runner](https://nodejs.org/docs/latest-v24.x/api/test.html) covers running and watching tests; [strict assertions](https://nodejs.org/docs/latest-v24.x/api/assert.html) covers checking values and errors.

Already using Jest or Vitest in your own project? Keep that runner. TDD is the feedback cycle, not a particular library.
