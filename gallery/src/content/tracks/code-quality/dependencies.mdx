## Trace a dependency's reach

Before changing a package, find what uses it and what could break. Choose a dependency in your own project, or investigate `d3-force` in the Lab.

### Follow the evidence

From the Lab root:

```sh
npm ls d3-force --workspaces
```

Confirm declarations in the consumer's `package.json`, then follow imports to callers. In `demos/dependency-map/`, `index.tsx` uses D3 for layout; `graph.ts` calculates dependency reach.

Map the chain from package to behaviour. For shared workspaces, follow their consumers too; keep a visited list to avoid cycles. Distinguish build tooling from browser code.

A manifest says a dependency is declared. An import shows use. Neither alone establishes whether a version change affects the API your app relies on.

### Choose proportionate checks

Identify the behaviour your proposed change could affect. For a D3 update, type compatibility and usable layout both matter. The Lab's existing check is:

```sh
npm run check --workspace @lab/demo-dependency-map
```

If you change it, inspect the running graph too. A passing build doesn't prove a usable interface. Broaden checks when shared consumers are affected.
