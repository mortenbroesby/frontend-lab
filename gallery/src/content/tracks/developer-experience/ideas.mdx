<Idea title="Faster Feedback Loops" summary="Compare targeted tests, watch mode and cached builds to get useful feedback sooner.">

**“I lose my train of thought while waiting to find out whether my change works.”** Explore targeted tests, watch modes, build caching and affected-project detection. Aim for useful feedback sooner while keeping the checks that matter.

Start with a real test in this repository or your own project. Run its test file, then select one named test and put it in watch mode. Make a small change and observe how quickly you get an answer. Compare the time and the scope: what would the smaller run miss?

For a different experiment, run one package’s build twice through Turbo and inspect whether the second run uses the cache. Change an input and explain what reruns. Stretch by inspecting affected tasks with a dry run before executing them, or investigating a cache miss. Keep broader validation for changes that need it; the shortest command is not always the right check.

Read: [Node test filtering and watch mode](https://nodejs.org/docs/latest-v24.x/api/test.html) and [Turborepo’s task-selection and dry-run options](https://turborepo.dev/docs/reference/run).

</Idea>

<Idea title="Developer Tools" summary="Try a debugger feature or build a small CLI that answers a recurring question.">

**“I keep doing the same little investigation by hand.”** Make one recurring question easier to answer: which scripts can I run, what changed in this package, or why does this event handler fire twice?

Start by trying an existing command or debugger feature. Compare `npm run`, `git diff --stat` and `git diff --check` with the information you wish they showed. Or try a conditional breakpoint or logpoint in a real interaction. You may already have the tool you need.

If a gap remains, build a small read-only CLI that answers one question—for example, listing package scripts with their workspace names. Try it against two real manifests and an invalid input. Stretch with a useful filter or machine-readable output, rather than building a general-purpose framework. The optional Node starter is there if you want it; it is not the main exercise.

Read: [Git diff options](https://git-scm.com/docs/git-diff) and [Node’s native argument parser](https://nodejs.org/docs/latest-v24.x/api/util.html#utilparseargsconfig).

<Idea title="Development Workflows" summary="Explore API mocking, workspace commands or a simpler local development setup.">

**“I cannot work on this screen until the environment behaves.”** Explore local API mocking, monorepo commands and reproducible development environments. Make one part of your workflow independent of a slow service or unnecessary setup.

Start with an app that makes a request. Override its response with an empty result, block the request or throttle the network, and inspect the UI. These are different experiments: an empty result tests content, blocking tests failure, and throttling exposes loading behaviour. Remove the override when you finish.

Compare a browser-only override with a mock response in an app you own. Which is easiest for a colleague to reproduce? Alternatively, compare a standalone package build with a filtered monorepo build, or ask a peer to try your documented local setup. Stretch by making one scenario repeatable or removing one unnecessary setup step.

Read: [Chrome DevTools local overrides](https://developer.chrome.com/docs/devtools/overrides) and [Turborepo run reference](https://turborepo.dev/docs/reference/run).

</Idea>

<Idea title="Agentic Workflows" summary="Turn a repeated task into a Codex or Copilot skill and check the results yourself.">

**“I explain the same task repeatedly, and still have to check what the agent actually did.”** Explore reusable Codex/Copilot skills, agent-assisted development and automated review. Choose a task whose result you can judge yourself.

Start with a read-only review of one small change. Specify the package, what to inspect, which actions are allowed and what evidence to return. Compare the findings with your own inspection and existing checks. Then put the same workflow in a skill and try it on another change: does it save explanation, stay within scope and produce useful evidence?

For a development experiment, ask an agent to make one small improvement and inspect its diff. For automated review, compare the repository’s Fallow audit with an agent review: where do they agree, miss something or report a false positive? Stretch by refining the workflow around an observed failure. Reusability is useful; a clean review is not proof of correctness.

Use Codex or Copilot if you already have access. You can also design and rehearse the workflow manually; this track requires no new account.

Read: [Codex skills](https://developers.openai.com/codex/skills) and [Copilot CLI skills](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills).
