<h2 id="start-heading">Make everyday development less frustrating.</h2>
<p>Waiting for a test, guessing why a screen is slow, or repeating the same investigation? Pick one thing that interrupts your work and try a better way to do it.</p>
<p>Bring a project you know, or use a Lab example. A useful result can be a shorter command, a repeatable debugging step or a clearer brief.</p>

</section>

<section aria-labelledby="options-heading">
<h2 id="options-heading">What would you like to improve?</h2>
<div className="track-options">
<section aria-labelledby="feedback-heading">
<h3 id="feedback-heading">Spend less time waiting for tests</h3>
<p>Run the test relevant to your change automatically whenever you save.</p>
<p>Start with one test. Break the behavior it checks, save and watch it fail. Fix the change and save again to see it pass.</p>
<a className="track-start-link" href="#/track/developer-experience/feedback-loop">Try running a test on save →</a>
<p className="track-example">The guide includes a small example you can run in the Lab. Afterwards, run the broader checks to see what the focused test doesn’t cover.</p>
</section>
<section aria-labelledby="profiling-heading">
<h3 id="profiling-heading">Find what makes an interaction slow</h3>
<p>Follow what happens when you type, open a panel or select an item.</p>
<p>Record one interaction in React Profiler. Find the work behind it before deciding what to change.</p>
<a className="track-start-link" href="#/track/developer-experience/rendering">Start recording an interaction →</a>
<p className="track-example"><DemoLink id="react-render-detective">Explore React Render Detective</DemoLink> to see why components update. Its counters explain renders; they do not measure interaction speed.</p>
</section>
<section aria-labelledby="responses-heading">
<h3 id="responses-heading">Reach the UI state you need</h3>
<p>Work on an empty list, a failed request or a slow response without waiting for the backend to produce it.</p>
<p>Open an app that makes a request. Override one response with an empty result and inspect what the screen does.</p>
<a className="track-start-link" href="https://developer.chrome.com/docs/devtools/overrides">Start with DevTools overrides ↗</a>
<p className="track-example">Chrome's external guide explains local response overrides. Try request blocking or throttling separately to explore failure and loading, then remove your overrides.</p>
</section>
<section aria-labelledby="agents-heading">
<h3 id="agents-heading">Stop repeating an agent brief</h3>
<p>Turn a task you keep explaining into a workflow you can reuse and check.</p>
<p>Start with a read-only review of one small diff. Specify the files, allowed actions and evidence you need, then compare the findings with your own inspection.</p>
<a className="track-start-link" href="https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills">Turn the brief into a Copilot skill ↗</a>
<p className="track-example">Or use the <a href="https://developers.openai.com/codex/skills">Codex skills guide</a>. Both are external resources. Try the workflow on a second change; you can rehearse it manually if you don't have an agent.</p>
</section>
</div>
</section>

<section className="track-method" aria-labelledby="method-heading">
<h2 id="method-heading">How to work on it</h2>
<ol>
<li><strong>Choose a recurring annoyance.</strong><p>Use one you can reproduce. Your own idea is welcome: a useful script, a debugger shortcut or one less setup step.</p></li>
<li><strong>Try one alternative.</strong><p>Keep the task the same so you can compare. Use an existing tool before building one.</p></li>
<li><strong>Keep what helps.</strong><p>Check whether it saves steps, gives a clearer answer or makes the task easier to repeat. Note what it misses before relying on it.</p></li>
</ol>
</section>
