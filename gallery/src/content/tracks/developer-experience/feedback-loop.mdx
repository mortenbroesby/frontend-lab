## Find your shortest feedback loop

Run the smallest relevant test while editing; broaden checks before committing.

Use the terminal exercises below to see real test results and cache decisions. Make one change, observe the result, then restore your edit.

### 1. Establish a baseline

From the root with Node 24, no install needed:

```sh
node --test gallery/exercises/tooling/commands.test.mjs
```

Expect four passes, including a CLI failure case. Note count and duration; this baseline covers one file, not the repository.

### 2. Narrow the question

Select the ordering test by name:

```sh
node --test --test-name-pattern="sorts commands" gallery/exercises/tooling/commands.test.mjs
```

Expect one pass; a misspelled pattern may select none. Check the count. Fewer tests may not run faster and omit CLI/invalid-input coverage.

### 3. Make feedback continuous

```sh
node --test --watch --test-name-pattern="sorts commands" gallery/exercises/tooling/commands.test.mjs
```

On your experiment branch, open `gallery/exercises/tooling/commands.mjs`. Change `a.localeCompare(b)` to `b.localeCompare(a)` and save: the test should fail. Restore only that edit: it should pass. Stop with Ctrl+C and rerun the full file.

This demonstrates regression detection without a wrapper. Compare your usual workflow; one run is not a benchmark.

### 4. Explore task selection and caching

After the normal root install:

```sh
npm exec -- turbo run build --filter=@lab/demo-react-render-detective --dry=json
npm exec -- turbo run build --filter=@lab/demo-react-render-detective
npm exec -- turbo run build --filter=@lab/demo-react-render-detective
npm exec -- turbo run build --affected --dry=json
```

Dry runs describe tasks without building. The filter selects React Render Detective. Without edits, the second build should hit cache; both may hit if cached already. Edit a source file: its next build must miss. Restore the edit.

Inspect JSON `tasks[].inputs`: demos track their files and shared kit; gallery also tracks all demo source. The dependency map tracks displayed manifests. Generated `dist` and `.turbo` logs are excluded.

Edit another demo: Render Detective should keep its cache while gallery rebuilds. Kit changes should invalidate consumers; root compiler/toolchain changes may invalidate everything. Compare hashes before removing inputs. Cached output must remain correct.

Affected selection needs Git history and a comparison base. Inspect the plan first; task selection and cache reuse are separate decisions.

Targeted passes do not replace broader checks your change needs.

References: [Node test filtering and watch mode](https://nodejs.org/docs/latest-v24.x/api/test.html) · [Turbo run options](https://turborepo.dev/docs/reference/run).

### Apply it in your project

Choose a test for the behaviour you are editing, using your existing runner's filter and watch options. Confirm the filter actually selects tests. Keep a broader check before committing changes that cross module boundaries.

If your project uses a task cache, inspect its inputs before trusting a hit. Change a dependency and confirm the affected consumer rebuilds. You do not need to adopt Turbo to use a focused test or watch mode.
