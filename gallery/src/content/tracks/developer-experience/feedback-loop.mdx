## Find your shortest useful feedback loop

Where do you lose time while changing code: waiting for checks, finding the right command or discovering mistakes too late? Choose one recurring interruption in your own workflow and investigate an alternative.

A useful loop gives you evidence about the change you're making. The shortest command isn't necessarily the best one if it leaves the relevant behaviour unchecked.

### Find the question behind a check

Choose a behaviour you're editing. Locate its implementation, callers and existing tests. What would a passing test establish—and what would it leave unknown?

Look up your runner's filtering and watch options. A filter narrows what executes; watch mode repeats checks after changes. They solve different problems. Confirm that a filter actually selects tests before trusting a green result.

If you need a small example, the Lab has `gallery/exercises/tooling/commands.mjs` and its adjacent test file. Run the existing checks from the root with Node 24:

```sh
node --test gallery/exercises/tooling/commands.test.mjs
```

Read a test and choose a behaviour to investigate. Use [Node's test runner documentation](https://nodejs.org/docs/latest-v24.x/api/test.html) to discover how to select that test and rerun it as you edit. Your own project's runner is equally suitable.

### Check the feedback, not just the command

Try a temporary change that you expect your selected test to detect. Does it fail for the reason you expected? Restore only that deliberate edit and confirm the test passes again. Don't commit an intentional defect.

If it stays green, investigate whether the filter missed the test or the test missed the behaviour. [Find a missing test](#/track/code-quality/test-confidence) explores that distinction.

Compare this loop with your usual one. Consider steps, waiting and clarity of feedback. A single timing isn't a benchmark, and fewer tests may not run faster.

### Investigate what can safely be skipped

Caching is a separate question: when is previous output still valid? Before adding a cache, find out whether task selection or watch mode already solves your problem.

For an existing Turbo project, the [run reference](https://turborepo.dev/docs/reference/run) explains filters, affected selection and dry runs. In the Lab, this inspects one demo's build plan without building it:

```sh
npm exec -- turbo run build --filter=@lab/demo-react-render-detective --dry=json
```

Explore `tasks[].inputs` and the project's `turbo.json`. Which source files, shared packages and configuration should invalidate the result? Affected selection depends on Git history and a comparison base; it isn't the same as a cache hit.

Choose a dependency you expect to matter. Compare the plan or cache behaviour before and after a temporary change, then restore your edit. Also consider an unrelated change: should it require the same work? Cached output must remain correct; removing inputs merely to get hits isn't an improvement.

### Keep the useful part

Keep a command or workflow if it answers your question with less friction. Decide when broader checks are still needed, particularly when a change crosses module boundaries. You can improve feedback without adopting Turbo or replacing your existing tools.
