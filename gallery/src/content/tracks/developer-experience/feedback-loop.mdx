## Find your shortest useful feedback loop

Where do you lose time: waiting for checks, finding commands or discovering mistakes late? Choose one recurring interruption. A faster command is useful only if it still checks what matters.

### Choose the evidence you need

Find the implementation, callers and tests for a behaviour you're editing. What would a pass establish—and leave unknown?

Investigate your runner's filtering and watch options. Filtering selects checks; watch mode repeats them. Confirm that your filter selects tests before trusting a green result.

For a small Lab example, inspect `gallery/exercises/tooling/commands.mjs` and its adjacent test file. From the root with Node 24:

```sh
node --test gallery/exercises/tooling/commands.test.mjs
```

Use the [Node test runner documentation](https://nodejs.org/docs/latest-v24.x/api/test.html) to investigate selection and watching, or use your own project's runner.

### Test the loop

Temporarily introduce a mistake your chosen test should catch. Does it fail for the expected reason? Restore only your deliberate edit and confirm it passes. Don't commit the defect.

If it stays green, did the filter miss the test or the test miss the behaviour? [Find a missing test](#/track/code-quality/test-confidence) explores that distinction.

Compare waiting, steps and clarity with your usual workflow. One timing isn't a benchmark.

### Decide what can be skipped

Before adding caching, check whether selection or watching solves the problem. For Turbo, inspect a plan without building:

```sh
npm exec -- turbo run build --filter=@lab/demo-react-render-detective --dry=json
```

Explore `tasks[].inputs`, `turbo.json` and the [run reference](https://turborepo.dev/docs/reference/run). Which source, dependencies and configuration should invalidate output? Test a relevant change and an unrelated one, then restore them. Removing necessary inputs to get cache hits makes results unreliable.

Affected selection requires Git history and a comparison base; it differs from cache reuse. Keep broader checks for changes that cross boundaries. You don't need new tools to improve your loop.
