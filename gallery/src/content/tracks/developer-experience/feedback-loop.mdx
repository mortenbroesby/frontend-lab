## Find your shortest useful feedback loop

**You changed one error message. Do you need to build every demo to find out whether it works?** Start with the check that answers that question, then broaden when the change affects more.

<div className="guide-flow" role="group" aria-label="A useful development feedback loop">
  <div><strong>Edit one behaviour</strong><span>Know what should change</span></div>
  <span aria-hidden="true">↓</span>
  <div><strong>Run a relevant check</strong><span>Confirm it actually selects your test</span></div>
  <span aria-hidden="true">↓</span>
  <div><strong>Read the result</strong><span>Fix the cause or widen the investigation</span></div>
</div>

### Try it: one message, one check

Inspect `gallery/exercises/tooling/commands.mjs` and `commands.test.mjs`. The small command-inventory tool has an empty-project message and a test for it. From the repository root with [Node 24](#/guide/setup):

```sh
node --test gallery/exercises/tooling/commands.test.mjs
```

Predict what happens if you change only that message. Make a temporary edit and rerun. **The relevant assertion should fail**, rather than a build or unrelated check. Restore your edit and confirm it passes.

Compare the work each command asks for:

| Command | What it tells you |
| --- | --- |
| The focused command above | Whether this file's tests pass |
| `npm run check` | Whether the repository's broader checks pass |

These are scopes, not speed claims. A green focused test doesn't establish that all consumers still work.

### Keep the loop running

Run the same test file in watch mode:

```sh
node --test --watch gallery/exercises/tooling/commands.test.mjs
```

Change the message again and save. Does the relevant test rerun without another command? Restore the edit, wait for green, then stop with Ctrl+C. Don't commit the deliberate defect.

**Filtering chooses checks; watching repeats them.** If a filtered run stays green after a deliberate mistake, inspect which tests ran before changing the implementation. [Find a missing test](#/track/code-quality/test-confidence) explores the other possibility: the assertion missed the behaviour.

### Explore caching after selection

A cache reuses a previous result. It only helps if every relevant input invalidates it. Inspect a Turbo plan without building:

```sh
npm exec -- turbo run build --filter=@lab/demo-react-render-detective --dry=json
```

Look at `tasks[].inputs` and `turbo.json`. Which source or configuration change should invalidate the output? Compare a relevant edit with an unrelated one; restore both. Don't remove necessary inputs just to get a hit.

**Your result:** a command you can use while editing, plus a clear reason to run broader checks. Try the same approach with your own runner. A single timing is not a benchmark, and Git-based affected selection is different from caching.

Read [Node's test runner](https://nodejs.org/docs/latest-v24.x/api/test.html) for selection and watch options, and [Turbo's run reference](https://turborepo.dev/docs/reference/run) for task plans and caching.
