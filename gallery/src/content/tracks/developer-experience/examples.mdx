# Find your shortest feedback loop

Run the smallest relevant test while editing; broaden checks before sharing.

- **Try:** [Open the command explorer](#/demo/tooling), choose **One behaviour** and run its command from the repository root.
- **Change:** Choose **Watch changes** and temporarily reverse the comparator in `demos/tooling/examples/commands.mjs`. Restore that edit afterwards.
- **Observe:** Does saving trigger a failing test, then a pass after restoring? Check test counts as well as timings.

The explorer supplies local commands, not simulated timings.

## 1. Establish a baseline

From the root with Node 24, no install needed:

```sh
node --test demos/tooling/examples/commands.test.mjs
```

Expect four passes, including a CLI failure case. Note count and duration; this baseline covers one file, not the repository.

## 2. Narrow the question

Select the ordering test by name:

```sh
node --test --test-name-pattern="sorts commands" demos/tooling/examples/commands.test.mjs
```

Expect one pass; a misspelled pattern may select none. Check the count. Fewer tests may not run faster and omit CLI/invalid-input coverage.

## 3. Make feedback continuous

```sh
node --test --watch --test-name-pattern="sorts commands" demos/tooling/examples/commands.test.mjs
```

On your experiment branch, open `demos/tooling/examples/commands.mjs`. Change `a.localeCompare(b)` to `b.localeCompare(a)` and save: the test should fail. Restore only that edit: it should pass. Stop with Ctrl+C and rerun the full file.

This demonstrates regression detection without a wrapper. Compare your usual workflow; one run is not a benchmark.

## 4. Explore task selection and caching

After the normal root install:

```sh
npm exec -- turbo run build --filter=@lab/demo-tooling --dry=json
npm exec -- turbo run build --filter=@lab/demo-tooling
npm exec -- turbo run build --filter=@lab/demo-tooling
npm exec -- turbo run build --affected --dry=json
```

Dry runs describe tasks without building. The filter selects the tooling demo. Without edits, the second build should hit cache; both may hit if cached already. Edit a source file: its next build must miss. Restore the edit.

Inspect JSON `tasks[].inputs`: demos track their files and shared kit; gallery also tracks all demo source. The dependency map tracks displayed manifests. Generated `dist` and `.turbo` logs are excluded.

Edit another demo: tooling should keep its cache while gallery rebuilds. Kit changes should invalidate consumers; root compiler/toolchain changes may invalidate everything. Compare hashes before removing inputs. Cached output must remain correct.

Affected selection needs Git history and a comparison base. Inspect the plan first; task selection and cache reuse are separate decisions.

**Show:** a red → green rerun, selected task or explained cache miss. Targeted passes do not replace broader checks your change needs.

References: [Node test filtering and watch mode](https://nodejs.org/docs/latest-v24.x/api/test.html) · [Turbo run options](https://turborepo.dev/docs/reference/run).

## Optional completed tool: command inventory

Compare the native `npm run` output with:

```sh
node demos/tooling/examples/commands.mjs gallery/package.json
```

This validates a manifest and lists sorted scripts without executing them. Source and four tests live in `demos/tooling/examples/`; the [optional starter](#/track/developer-experience/get-started) is independent. Keep the utility only if useful.
