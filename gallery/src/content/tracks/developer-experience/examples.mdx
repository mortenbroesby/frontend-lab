# Worked example: find your shortest feedback loop

**Friction:** running broad validation after every small edit interrupts your flow. **Alternative:** run the smallest relevant test while editing, then broaden validation before sharing.

[Open the command explorer](#/demo/tooling) to switch between targeted tests, watch mode, cached builds and affected-project plans. It shows real commands to run locally, not simulated timings.

## 1. Establish a baseline

From the repository root, with Node 24 (no install needed), run the completed command-inventory tests:

```sh
node --test tracks/developer-experience/examples/commands.test.mjs
```

Expect four passing tests, including a real CLI failure case. Note the test count and reported duration. This is a file-level baseline, not the whole repository suite.

## 2. Narrow the question

If you are changing command ordering, select its behaviour by name:

```sh
node --test --test-name-pattern="sorts commands" tracks/developer-experience/examples/commands.test.mjs
```

Expect one passing test. A misspelled pattern can select zero tests: check the count. A smaller selection is not automatically faster on a tiny suite, and does not cover the CLI or invalid-input cases.

## 3. Make feedback continuous

```sh
node --test --watch --test-name-pattern="sorts commands" tracks/developer-experience/examples/commands.test.mjs
```

On your experiment branch, open `tracks/developer-experience/examples/commands.mjs`. Temporarily reverse the comparator from `a.localeCompare(b)` to `b.localeCompare(a)`. Save: the ordering test should fail. Restore that single edit and save: it should pass. Stop watching with Ctrl+C, then rerun the full file. Keep unrelated edits intact.

You have demonstrated that your editing loop catches the relevant regression. Compare it with your usual workflow; do not infer a benchmark from one run. No new wrapper script was necessary.

## 4. Explore task selection and caching

After the normal root install:

```sh
npm exec -- turbo run build --filter=@lab/demo-tooling --dry=json
npm exec -- turbo run build --filter=@lab/demo-tooling
npm exec -- turbo run build --filter=@lab/demo-tooling
npm exec -- turbo run build --affected --dry=json
```

The dry runs describe tasks without building them. The explicit filter selects the tooling demo; inspect whether the second build uses its local cache. In our verification, both runs missed—an investigation opportunity, not a required speedup. Affected selection needs Git history and a usable comparison base; inspect the plan before executing it.

**A real constraint to investigate:** this repository includes broad `globalDependencies` in `turbo.json`, including generated `dist` files and `.turbo` logs in the inspected dry-run plan. Those files can change during a build and invalidate the next run; unrelated source edits can also invalidate several cache keys. Affected selection and cache validity answer different questions. Inspect `globalCacheInputs.files` in the JSON. On your experiment branch, try excluding generated outputs from the inputs, run twice, then change a real source file and confirm it still invalidates the build. Compare the plans/hashes before deciding whether the input change is safe. The gallery bundles all demos; do not remove its real dependencies just to improve a cache number.

**Demonstrate:** show the red → green test rerun, the selected task or an explained cache miss. A targeted pass does not replace the broader checks needed for your actual change.

References: [Node test filtering and watch mode](https://nodejs.org/docs/latest-v24.x/api/test.html) · [Turbo run options](https://turborepo.dev/docs/reference/run).
