## Profile a React interaction

**You edit a collection's note. Why do its unchanged tiles render?** Open <DemoLink id="react-render-detective">React Render Detective</DemoLink> and predict which of its three lanes will skip tile renders when you press **Update parent**.

### Predict, then try

Press **Update parent** in each lane. Compare the tile counters before and after:

| Lane | What to watch for |
| --- | --- |
| No memo | Children render with the parent |
| Memo, new object | A freshly created object defeats the shallow prop comparison |
| Memo, stable prop | Reusing the existing object lets the tiles skip this update |

The demo's tiles are deliberately cheap. **These counters explain renders; they don't measure speed.** Exact development counts matter less than which updates reach the tiles.

Follow the difference in `demos/react-render-detective/experiment.tsx` and `tile.tsx`. What changes if a tile owns state of its own?

### Find work that matters

Choose a reproducibly slow interaction in your own app. Record it with [React Developer Tools](https://react.dev/learn/react-developer-tools), then inspect the commit in Profiler's flamegraph or ranked view. Repeat so startup work doesn't dominate the conclusion.

Look for evidence before choosing a fix: state high in the tree, recreated props or expensive work repeated with unchanged inputs. A component rendering isn't itself a bug.

### Change one thing

Try the smallest change the recording supports. Repeat the same interaction with the same data and environment. Did the work or responsiveness improve? Remove the change if it doesn't help; don't memoise everything.

Use the browser Performance panel when scripting, layout or painting outside React may dominate. Development checks and profiling add overhead, so fewer commits alone don't prove a faster interface.

**Done:** you can connect one observed cost to one change and explain the comparison.
