## Profile a React interaction

Learn to record a React interaction, identify the work behind it and evaluate one improvement. The outcome is a repeatable profiling workflow; you don't need to add memoisation to succeed.

### 1. Pick an interaction and record it

Use an existing React app with a slow interaction you can reproduce: typing in a filter, opening a panel or selecting an item. Run it locally and install [React Developer Tools](https://react.dev/learn/react-developer-tools) for your browser if it isn't available. It adds Components and Profiler panels to browser developer tools.

Open Profiler, start recording, perform the interaction once and stop. Select the commit associated with that action. Use the flamegraph or ranked view to identify components that account for the work; inspect their props and state in Components. Record the same interaction more than once to avoid drawing conclusions from startup or an unusual run.

If you don't have a suitable app, <DemoLink id="react-render-detective">React Render Detective</DemoLink> is an optional controlled example. Its tiles are deliberately cheap: use it to learn to read updates, not to claim a performance win.

### 2. Follow the update to its cause

Find the state update triggered by the interaction. Then follow the affected component's inputs in source:

- Does state live higher in the tree than necessary?
- Does the parent create a fresh object or callback on every render?
- Is an expensive calculation repeated with unchanged inputs?

A component rendering again is normal. Focus on work that affects the interaction rather than trying to eliminate all renders. A stable prop only helps a memoised component skip a parent-driven update; its own state and context can still cause updates.

In the Lab reference, compare `experiment.tsx` and `tile.tsx` under `demos/react-render-detective/`. The ordinary, fresh-object and stable-object cases make that distinction visible. Commit counters aren't measurements of interaction speed.

### 3. Make one change and compare

Choose a change supported by the recording: move state closer to its owner, avoid repeating an expensive calculation, or stabilise a prop where memoisation is useful. Preserve the values and behaviour the component needs. Don't add memo everywhere.

Record the same interaction with the same data and environment. Compare several runs and check the behaviour as well as the profile. If the change doesn't help, remove it; understanding that a component wasn't the bottleneck is a useful result.

Development checks and profiling instrumentation add overhead. Use React profiling to locate work, then the browser Performance panel when you need to understand scripting, layout, painting and the complete interaction. Fewer React commits alone doesn't prove a faster app.

### Take it further

Compare moving state with memoising a child. Or profile filtering a larger dataset and determine whether the next improvement belongs in rendering, the calculation, or a [Web Worker](#/track/modern-web/workers).
