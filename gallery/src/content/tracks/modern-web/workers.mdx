## Give an interaction room to respond

**A calculation is running. Can you still tap a button?** Open <DemoLink id="web-worker-comparison">Room to think</DemoLink> and use the interaction pad during both execution modes, with the same workload.

Watch the interaction, not just the finish time. Moving work can make the page more responsive without making the calculation finish sooner. Choose something you want to keep usable: typing, dragging, cancelling or navigating.

Check [Web Workers browser support on Can I Use](https://caniuse.com/webworkers), including the support notes for the features you plan to use.

### Find the boundary

A Worker runs JavaScript away from the main thread, without direct access to the DOM or React state. Which calculation could run using only its input and return a result?

Check a Performance recording first. A Worker won't solve a bottleneck in layout or painting.

In `demos/web-worker-comparison/`, trace `compute.ts` → `compute.worker.ts` → `index.tsx`: calculation, message handling, then interface updates. `frames.ts` observes animation-frame gaps. Use [MDN's Worker guide](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers) and [Vite's Worker support](https://vite.dev/guide/features.html#web-workers) for implementation details.

Messages have a cost: ordinary objects are cloned. Validate inputs, bound expensive work, handle errors and release unused Workers.

### Compare and decide

Adapt the demo or use your own app. Compare the same calculation and input in both modes, repeating the interaction. One run isn't a benchmark.

Investigate what your interaction needs:

- **Changing input:** can an old result overwrite a newer one? Request IDs can distinguish jobs.
- **Cancellation:** does work stop or merely disappear? A synchronous loop can't process cancel messages until it yields; consider termination or chunking.
- **Small jobs or large payloads:** does messaging outweigh the benefit?

Keep work on the main thread if the evidence supports it.
