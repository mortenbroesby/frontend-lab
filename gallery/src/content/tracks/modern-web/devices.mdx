## Make something happen on another screen

Choose an interaction: shared drawing, reactions, a remote control—or your own idea. A tap on one device becomes a message that changes another. What needs to travel, and what can stay local?

### Start with a shared reaction wall

<DemoLink id="reaction-room">Reaction Room</DemoLink> turns the creator’s browser into a host. Open it over HTTPS, create a room, and share its code or QR link. Everyone joins directly from their browser—no server command or account.

Keep the creator’s page open and awake, preferably on a laptop. PeerJS’s public signalling service introduces the browsers; reactions then travel over WebRTC through the host. Internet is needed, and some networks block these connections. Try a smaller group or another network if joining stalls.

### Follow one reaction

- **Connect:** each guest finds the host using the room code. Guests do not connect to each other.
- **Send:** `use-reaction-room.ts` batches rapid taps. `connect-room.ts` manages the WebRTC connections through PeerJS.
- **Forward:** `host-room.ts` validates batches and sends them to the other connected screens. The sender already showed its own tap locally.
- **Render:** `reaction-motion.ts` turns recent reactions into pulses and heat. Animation frames never cross the network.

A reaction is an event; a selected colour is state. New arrivals receive future reactions, not a replay. Try changing that distinction: what would a shared drawing or collaborative colour picker need when someone joins late?

### Choose an experiment

**Change what the group controls.** Replace reactions with votes for a colour, a shared tempo or a collaborative drawing. Begin by defining the smallest message that represents one action.

**Explore disconnection.** Close one window, reconnect, or close the host page. Decide whether your experiment should discard missed events, replay them or send a fresh state snapshot. Compare the result on two screens.

**Compare connection shapes.** The <DemoLink id="canvas-tv">Canvas TV</DemoLink> phone remote uses Trystero for one-to-one pairing. Compare that with Reaction Room’s host-and-guests design. What happens if the host leaves? Could a new host take over, and what state would it need?

### Useful starting points

Check [WebRTC browser support on Can I Use](https://caniuse.com/rtcpeerconnection). Browser support does not guarantee that a corporate network will allow the connection.

- [MDN: WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) — send and receive messages over a browser connection.
- [PeerJS](https://peerjs.com/docs/) — connect browsers through a public signalling service without operating your own server.
- [Trystero](https://github.com/dmotz/trystero) — peer discovery and WebRTC messaging without building your own signaling flow.
- [MDN: WebRTC protocols](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols) — signaling, STUN and TURN.

Use throwaway data: room codes are shareable labels, not passwords. A successful local experiment does not prove every network will allow the same connection. For same-browser tabs, [explore BroadcastChannel](#/track/modern-web/tab-settings).
