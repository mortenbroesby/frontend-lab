## Make something happen on another screen

A phone could control a slide, two browsers could share a drawing, or a button could send a reaction across the room. Choose an interaction you'd like to explore—or invent your own.

Try <DemoLink id="device-rally">Device Rally</DemoLink> in two browsers. Send a cheer, disconnect one browser and join again. Notice which information stays on each screen and which travels between them. Use the demo as a reference when you need it; your experiment can work differently.

### Understand the connection

There are three separate jobs behind a cross-device interaction:

- **Discovery:** browsers need a way to find peers. Trystero uses signaling services to introduce browsers with the same app ID and room code.
- **Connection:** WebRTC establishes a path between peers. Finding another browser doesn't guarantee the network will let them connect.
- **Messages:** your application decides what to send and what a received message means for its interface.

[Trystero's documentation](https://github.com/dmotz/trystero) is a starting point for rooms and messages. [MDN's WebRTC protocol guide](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols) explains the network side, including STUN and TURN.

### Choose what needs to travel

Start with one visible effect on the receiving screen. Before implementing it, decide what information that screen needs.

A reaction is an **event**: something happened. A selected colour is **state**: something is currently true. That distinction matters when someone joins late. Should they see only future changes, or receive the current value too? Messages aren't automatically a shared history.

You could explore a remote control, a shared pointer or a cooperative game. Pick whichever interests you; one interaction is enough to start.

### Find your way into the code

Work in your own app, adapt Device Rally or [create a Lab demo](#/create). For a new Lab workspace, this installs the version used by Device Rally; replace `your-id` with your demo's folder ID:

```sh
npm install --save-exact trystero@0.27.0 --workspace @lab/demo-your-id
```

Use the documentation alongside `demos/device-rally/index.tsx`. Follow one cheer from the button to the receiving screen, then find the parts your idea needs:

| What you're investigating | Where to look |
| --- | --- |
| How browsers find the same group | `joinRoom`, the app ID and room code |
| How an interaction becomes a message | `makeAction` and `send` |
| How a message changes the interface | `onMessage` and the receiving state update |
| How the interface knows someone is connected | Peer join and leave listeners |
| What happens when the component unmounts | Listener cleanup and `leave` |

The demo separates connection state from the cheer count. Keep that distinction visible while experimenting: “no peer connected” and “connected but no message received” point to different problems. Check received data before using it; TypeScript types don't validate a network message.

### Try to break your assumption

Once your interaction works, choose a change that tests how you think it works:

- **Send from the other browser.** Is the interaction symmetric, or does one screen have a different role?
- **Join after something changes.** Does the new screen have enough information to show the right thing?
- **Close and reopen a browser.** Does it reconnect cleanly? Does one message still produce one update?

Use what happens to choose your next change. You don't need to implement every behaviour above.

### When nothing connects

Start with two windows on **localhost**, internet access and matching app IDs and room codes. Use a room code unique to your experiment. This setup uses public signaling; a room name isn't authentication, so use throwaway data.

For separate computers, each can run its own local copy. A phone visiting your laptop needs **trusted HTTPS**; plain HTTP at a LAN address isn't supported by this setup. Two local windows help isolate application problems, but don't prove that a particular device or network will work.

If discovery works but the connection doesn't, network restrictions may be the cause. TURN can relay connections that can't go directly between peers; setting up a relay is beyond this experiment. Use the MDN guide above to understand that distinction before changing your application logic.
