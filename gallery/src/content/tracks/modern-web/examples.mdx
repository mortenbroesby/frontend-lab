You can experience the result first, rebuild a small version in your generated `demos/<your-idea>/index.tsx`, inspect the reference only when stuck, or take an entirely different API direction. ## D3: follow a dependency ripple

**Experience:** Open [Dependency ripple](#/demo/constellation). Compare `react-dom`, `react`, `d3-force` and `@lab/demo-kit`: which reaches the most workspaces? Select a package to highlight direct and indirect consumers. Switch between dependency layers and a force layout, drag nodes, or use arrow keys to pin them. The package selector and consumer list provide another way to explore. Reduced motion starts paused.

**Learn:** Arrows point from consumer to dependency. Change impact travels backwards along those arrows. A highlighted consumer may need checking; it is not automatically broken. Layout affects where things appear, not their relationships.

**Build towards it:** Start with three labelled SVG circles and two directed edges. Add one D3 force, then highlight the consumers of a selected node. `demos/constellation/graph.ts` contains the small traversal; `data.ts` reads this repository's manifests at build time. Add a dependency to a demo manifest, reload locally and find its new edge. Rebuild deployed output to refresh its snapshot.

**Understand the boundary:** This shows declared workspace dependencies and devDependencies, not source imports, versions or the complete transitive npm tree. External packages are leaves. D3 owns mutable simulation nodes; React renders position snapshots. Links are copied before D3 resolves endpoints into objects, and the simulation stops on unmount.

**Remix:** Replace the manifest dataset with routes and components, services and callers, or characters and relationships. Keep one clear meaning for an edge. Optional stretch: distinguish runtime from development edges, or show the shortest path to an affected workspace.

References: [D3 force simulations](https://d3js.org/d3-force/simulation), [link forces](https://d3js.org/d3-force/link). D3 is a library on top of browser capabilities, not a native browser API. The completed demo is an optional destination, not a checklist to rebuild.

## Door 1: draw something surprising

**Experience:** In the SVG example, adjust the dot count, remix and save an image. Notice that the same seed produces the same result.

**Build towards it:** Start with one SVG circle. Add an array of circles, then one control. If useful, borrow `makeDots` from `demos/art/art.ts`; alternatively invent your own distribution. The finished reference is `demos/art/index.tsx`.

**Branch:** Spiral instead of random scatter; data-driven sizes; pointer interaction; a game of finding a dot; keyboard controls or reduced motion. Optional export is already demonstrated by serialising SVG into a downloadable Blob.

**Question worth keeping:** When would SVG suit this better than Canvas? What information would a person need if they could not see the image?

## Door 2: keep the interface listening

**Experience:** Run the calculation in a Worker and use the interaction pad. Compare it on the main thread, starting small. A quick run may be hard to perceive; inspect a trace or increase the bounded workload.

**Build towards it:** Start a Worker that receives a number and replies with a result. Then move one pure computation into it, show its status and add cancellation by terminating the Worker. References: `index.tsx`, `compute.worker.ts` and `compute.ts` under `demos/workers`.

**Branch:** Progress messages, image processing, search, or producing a large array of points for your SVG. Think about data-transfer cost, cancellation and stale results when inputs change.

**Evidence:** Record workload, browser/device and whether interaction remains available. The displayed time measures computation, not Worker startup or messaging. Off-thread work does not guarantee faster execution.

## Door 3: let two tabs talk

**Experience:** Open the second lab tab from the signals example. Send a message and observe that only the other tab receives it. Close and reopen a tab: there is no saved history.

**Build towards it:** Create a `BroadcastChannel`, send a string, display received strings and close the channel when the component leaves. Reference: `demos/signals/index.tsx`. Keep both tabs on the exact same origin.

**Branch:** Share a palette, quiz question or simple drawing event between tabs. Decide how to distinguish event types, handle invalid messages or avoid feedback loops.

**Scope:** BroadcastChannel connects local tabs. For separate computers, try the next example.

## Door 4: connect separate devices

**Experience:** Open [Device Rally](#/demo/device-rally) in two browsers with the same room code and send emoji cheers. Leave and rejoin to see peer discovery in action.

**Build towards it:** Use Trystero to join a room and exchange one event type. The finished reference lives in `demos/device-rally/`; `gallery/docs/DEVICE-RALLY.md` contains the setup and network details.

**Boundary:** Discovery needs internet access; the page needs localhost or trusted HTTPS. No custom backend is required, but restrictive networks may block WebRTC. Physical phones and the workshop network remain untested.

## Other doors remain open

View Transitions, Canvas, browser scheduling, WebAssembly and other APIs are valid choices. Find a minimal documented example, establish browser support and keep the first result small. No one is expected to try every API.
