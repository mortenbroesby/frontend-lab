## What could a dependency change affect?

Before changing a shared package, identify which workspaces deserve a closer look. A dependency graph gives you a starting point for investigation—not proof that an upgrade breaks them.

### Trace one change

<DemoLink id="dependency-map">Open Dependency ripple</DemoLink>.

1. Select `d3-force`. Follow the highlighted consumers back to their package manifests.
2. Select `react-dom`. Find a consumer more than one hop away. Trace the intermediate workspace that connects it.
3. Compare `react` and `@lab/demo-kit`. Which change would lead you to inspect more workspaces?
4. Switch layouts. The positions change; the dependency paths and affected consumers should stay the same.

Arrows point from a consumer to its dependency. To investigate a change, travel in the opposite direction: dependency → consumer → that consumer’s consumers. “Affected” here means reachable through declared dependencies, not confirmed runtime impact.

### Read the evidence

The demo reads workspace `package.json` files in `demos/dependency-map/data.ts`. It includes `dependencies` and `devDependencies`; external packages are leaves. It does not inspect source imports, lockfile versions or the dependencies of external packages.

`graph.ts` follows incoming edges and records each consumer’s shortest distance from the selected package. D3 arranges the picture; it does not decide which consumers are affected.

For one highlighted workspace, open its manifest and find the declaration that explains the edge. Then inspect the code that uses that dependency. A manifest alone cannot tell you whether the API you plan to change is used.

### Try it in your project

Choose a shared package you expect to change. You do not need a graph UI:

1. Find its direct consumers in your repository’s package manifests.
2. Repeat for those consumers until you have the relevant workspace chain.
3. Check actual imports and calls along one path. Separate build tools from browser runtime dependencies.
4. Run a focused test, type check or build for that consumer using your repository’s scripts. Expand checks when the evidence calls for it.

Your outcome is a short explanation: “This workspace depends on the changed package through this path; this check exercises the behaviour I changed.” For enforcing source-import boundaries, use [Protect an architecture boundary](#/track/code-quality/architecture).

To adapt this demo, replace the manifest glob in `data.ts` with your workspace locations. Rebuild hosted output after manifest changes; it is a build-time snapshot.
