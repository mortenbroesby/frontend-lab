# Developer Experience & Tooling worked example · What commands can I run in this project?

## Problem

A developer joining an unfamiliar project wants to see its defined commands without searching a larger manifest. The [bootstrap](#/track/developer-experience) can identify a project; this finished example turns that into a sorted command inventory.

This is an illustrative onboarding problem, not a claim that participants need another tool. `npm run` already lists scripts in a project. Discovering that native feature may be a better outcome than maintaining this script.

## Experience it

From the repository root, with Node 24.x and no package installation:

```sh
node tracks/developer-experience/examples/commands.mjs playground/package.json
node --test tracks/developer-experience/examples/commands.test.mjs
```

Expect alphabetically ordered script names and their actual commands, including `check`, `dev` and `test`. The report only reads the supplied manifest; it does not execute scripts, traverse the repository or contact a service.

## Approach and evidence

`tracks/developer-experience/examples/commands.mjs` reads JSON, validates its shape, sorts the scripts and prints a report. Tests cover sorting, empty projects, malformed values and missing-file errors. The starter and this example are independent: no finished logic is imported into your starting script.

Compare its output with the `scripts` section in `playground/package.json`. The tests demonstrate behaviour; they do not demonstrate time saved. Ask a peer which output helps them and whether `npm run` was enough before deciding to keep or expand it.

## Branch or stop

Maybe your real need is clearer commands, documenting required environment variables or shortening a feedback loop. Build towards one useful result from your starter rather than adding every report. This script does not detect unused scripts, validate their safety or prove they work.
